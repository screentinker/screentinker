Self-Hosted Digital Signage Software: Deployment Guide (2026)

Why you might want to self-host your digital signage CMS, what you need to do it well, and how to deploy ScreenTinker on your own server.

Why self-host digital signage?

Most digital signage products are cloud-only. That works for many businesses, but there are real reasons to keep the server in-house:

  • Data sovereignty. Healthcare, finance, government, and education often cannot put internal information into a third-party cloud. Self-hosting keeps content, schedules, and access logs on your network.
  • Cost control. Per-screen monthly fees stack up fast. Self-hosting trades that for a fixed server cost - typically $5 to $50 per month for a small VPS that can run hundreds of screens.
  • Network isolation. Some deployments live on private LANs with no internet access at all. Self-hosting is the only way to manage signage in those environments.
  • No vendor lock-in. If the cloud vendor disappears, raises prices 3x, or pivots away from your use case, your deployment goes with them. Self-hosters control their own roadmap.
  • Customization. Open source self-hosted means you can fork the code, add a custom widget, or wire it into your existing systems.

What you need

Hardware / VPS

A modest Linux server is enough for most deployments:

  • Up to 25 displays: 1 vCPU, 1 GB RAM, 20 GB disk. ~$5/month on Hetzner, DigitalOcean, or Vultr.
  • 25-100 displays: 2 vCPU, 2 GB RAM, 40 GB disk. ~$12-20/month.
  • 100+ displays: 4+ vCPU, 4+ GB RAM, faster disk. Plan for content storage at ~50-200 MB per screen depending on media volume.

An on-prem VM works just as well as a cloud VPS - in fact, on-prem is often the whole point.

Software prerequisites

  • Node.js 22.14 or newer
  • A supported Linux host, such as Ubuntu 22.04/24.04 or Debian 12, with Python 3, make and a C++ compiler
  • Optional ffmpeg for video thumbnails and duration extraction
  • A hostname and HTTPS for Internet access, provided by a public reverse proxy, Cloudflare Tunnel, or the app's TLS listener

Docker is also available. See the README self-hosting instructions for platform requirements and deployment options.

Deploying ScreenTinker

To run the server locally:

git clone https://github.com/screentinker/screentinker.git
cd screentinker/server
npm ci
cp ../.env.example .env
npm start

The server uses HTTP on port 3001. With app TLS certificates configured, HTTPS uses port 3443 and HTTP redirects to it. The first account becomes the platform administrator.

Before public access

  • Complete initial setup privately. Create the first administrator while the server is reachable only from your machine or trusted network. DISABLE_REGISTRATION=true blocks later self-service signups but still allows first-user setup on an empty database.
  • Set a fixed public address. Set APP_URL to the URL users visit so password-reset, verification and invitation links use that address.
  • Preserve the signing secret. Leave JWT_SECRET unset to use the generated certs/.jwt_secret. Changing it invalidates sessions and makes saved encrypted credentials unreadable. Back it up securely.
  • Use HTTPS and restrict backend access. When using a proxy or Tunnel, keep the app port private.

Reverse proxy or Cloudflare Tunnel

Use the shared Nginx or Caddy configuration for a public proxy. A dashboard-managed Cloudflare Tunnel can connect directly to the app; a local proxy is optional. Keep the app's route-specific security headers rather than adding a second policy at the proxy.

The operations runbook covers deployment choices, forwarded client IPs and Fail2ban enforcement.

Running as a service and collecting logs

Follow the README production deployment for the systemd service.

The supplied systemd units save logs to /var/log/screentinker/server.log, with logrotate for retention. Docker collects logs through its container logging configuration.

HTTP access logging is off by default; set ACCESS_LOG=true to enable it. Password/TOTP failure events remain enabled and can feed Fail2ban. Fail2ban requires separate setup and an action suited to the deployment: a host firewall for direct connections, or Cloudflare's API for Tunnel traffic. See server logs and Fail2ban.

Backups

Preserve the database, uploaded media, signing secret and service configuration:

  • server/db/remote_display.db — database
  • server/uploads/ — uploaded media
  • server/certs/.jwt_secret, or your configured JWT_SECRET — needed to decrypt saved credentials
  • Your environment, TLS keys and any other persistent data used by the deployment

These are the default native paths; DATA_DIR or individual path settings can relocate them. Docker keeps its state under /data. The README backup procedure covers database and media snapshots. Back up the secret and configuration separately.

When the cloud is the right answer

Self-hosting is not free of cost - it requires someone who can run a Linux server, monitor it, and apply security updates. If your screen count is small (under ~10) and you do not have IT capacity, the managed cloud version is probably the right choice. See the hosted plans for current pricing.
